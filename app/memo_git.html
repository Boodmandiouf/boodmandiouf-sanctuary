    Éviter GitHub Actions [skip ci]

    Ce n’est pas un attribut Git : c’est le message du commit qui décide.

    git commit -m "Mise à jour du README [skip ci]"
    Mot-clé reconnu
    [skip ci]
    [ci skip]
    [no ci]
    [skip actions]
    [actions skip]

    Ou avec un trailer, dans le corps du message :

    git commit -m "Changement de doc" -m "skip-checks: true"
    Le mot-clé doit être dans le dernier commit du push. Sans effet sur workflow_dispatch et schedule.

    Branches travailler sans risque 
    git branch                    # lister les branches locales
git switch -c ma-branche      # créer et basculer

git branch -d ma-branche      # supprimer en local
git push origin --delete ma-branche   # supprimer sur le dépôt

    .gitignore ne pas suivre certains fichiers

    Crée un fichier .gitignore à la racine du projet :

    node_modules/
dist/
*.log
.env
.DS_Store
.vscode/
!important.log   # le ! force l’inclusion

    Règles de motif

    • dossier/ ignore un dossier entier
    • *.ext ignore tous les fichiers de cette extension
    • /fichier ignore seulement à la racine
    • **/temp ignore à n’importe quelle profondeur

    Fichier déjà suivi par Git

    Ajouter une ligne ne suffit pas : il faut le retirer de l’index (le fichier reste sur ton disque).

    git rm --cached fichier.txt
git rm -r --cached dossier/
git commit -m "Retire fichier du suivi"
    git check-ignore -v fichier.txt   # pourquoi un fichier est ignoré
    Ne commit jamais un .env ou des clés d’API. Si c’est déjà poussé, considère la clé comme compromise et change-la.
    Résoudre un conflit merge ou pull

    Un conflit apparaît quand deux personnes modifient les mêmes lignes. Git s’arrête et marque le fichier :

    <<<<<<< HEAD
ta version
=======
la version de l’autre branche
>>>>>>> ma-branche

    Étapes

    git status                    # repérer les fichiers "both modified"
# 1. ouvrir le fichier, garder ce qu’il faut,
#    supprimer les lignes <<<<<<< ======= >>>>>>>
git add fichier.txt           # 2. marquer comme résolu
git commit                    # 3. finaliser le merge

    Raccourcis

    git checkout --ours fichier.txt     # garder ta version
git checkout --theirs fichier.txt   # garder l’autre version
git merge --abort                   # tout annuler, retour avant le merge
    Pour éviter les conflits : git pull souvent, commits petits, branches courtes.
    Annuler une erreur restore, reset, revert, rm
    Règle d’or : tant que le commit n’est pas poussé, tu peux l’annuler avec reset. Une fois poussé, utilise revert.

    Avant le commit

    git restore fichier.txt          # annuler les modifs (PERDUES)
git restore --staged fichier.txt # retirer du git add, modifs gardées

    Dernier commit pas encore poussé

    git commit --amend -m "Nouveau message"  # corriger le message
git reset --soft HEAD~1    # annule le commit, fichiers restent prêts à commit
git reset HEAD~1           # annule le commit, fichiers modifiés non ajoutés
git reset --hard HEAD~1    # annule le commit ET supprime les modifs

    Commit déjà poussé

    git revert <hash>          # crée un commit qui annule l’ancien
git push

    Si tu es seul sur la branche et tu veux vraiment réécrire l’historique :

    git reset --hard HEAD~1
git push --force-with-lease
    --force-with-lease est plus sûr que --force : il refuse d’écraser le travail d’un autre. À éviter sur main partagé.

    Supprimer / retirer des fichiers

    git rm fichier.txt           # supprime du disque ET du suivi
git rm --cached fichier.txt  # arrête le suivi, garde le fichier
git rm -r dossier/           # idem pour un dossier
git mv ancien.txt nouveau.txt # renommer / déplacer
git commit -m "Supprime fichier.txt"

    Panique ! je me suis trompé

    J’ai commité sur la mauvaise branche (pas poussé)

    git switch -c bonne-branche   # garde le commit sur une nouvelle branche
git switch main

    J’ai poussé un mot de passe ou une clé

    • D’abord : révoque et change la clé. Elle est compromise, même si tu la supprimes ensuite.
    • Retire-la de l’historique avec git filter-repo (outil à installer à part), puis force le push.
    git filter-repo --path .env --invert-paths
git push --force-with-lease origin main

    Annuler un merge

    git merge --abort               # merge en cours (conflits)
git reset --hard ORIG_HEAD      # merge fini, pas poussé
git revert -m 1 <hash-du-merge> # merge déjà poussé

    Cherry-pick et stash récupérer, mettre de côté

    cherry-pick : copier un commit d’une autre branche

    git log --oneline autre-branche   # repérer le hash
git switch main
git cherry-pick <hash>
git cherry-pick h1 h2 h3          # plusieurs commits
git cherry-pick h1^..h3           # une plage
git cherry-pick --continue        # après un conflit résolu
git cherry-pick --abort

    stash : mettre des modifs de côté

    git stash push -m 'travail en cours'
git stash push -u -m 'avec fichiers non suivis'
git stash list
git stash show -p stash@{0}       # voir le contenu
git stash pop                     # appliquer et supprimer
git stash apply stash@{1}         # appliquer et garder
git stash drop stash@{0}
git stash clear                   # tout supprimer

    Git ouvre un éditeur : remplace pick au début de chaque ligne par l’action voulue.

    ActionEffet
    pickgarder le commit tel quel
    rewordchanger le message
    squashfusionner avec le précédent, en gardant les messages
    fixupfusionner avec le précédent, message jeté
    dropsupprimer le commit
    git pull --rebase                 # pull sans commit de merge
    Ne rebase jamais une branche que d’autres utilisent : tu réécris l’historique.

    Workflow GitHub Actions exemple complet

    Fichier .github/workflows/ci.yml :

    name: CI
on:
  push:
    branches: [main, develop]
    paths-ignore:
      - '**.md'
      - 'docs/**'
  pull_request:
    branches: [main]
  workflow_dispatch:

jobs:
  build:
    if: ${{ !contains(github.event.head_commit.message, '[skip build]') }}
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm test
    • branches limite aux branches voulues (branches-ignore pour exclure).
    • paths-ignore ne lance rien si seuls des fichiers .md ou docs/ changent.
    • if saute le job quand le message contient [skip build], un mot-clé à toi.
    • workflow_dispatch permet de le lancer à la main.
    [skip ci] marche sans rien écrire dans le fichier. La condition if n’est utile que pour un mot-clé personnalisé. Sur une pull request, le message de commit n’est pas lu par cette condition : le job se lance.

    Connaître la taille sur GitHub

    Ouvre cette adresse dans le navigateur et cherche la ligne size :

    https://api.github.com/repos/TON-USER/TON-REPO

    La valeur est en Ko : divise par 1024 pour avoir des Mo (exemple : 7931 Ko, soit environ 7,7 Mo). Elle inclut tout l’historique Git.

    gh api repos/TON-USER/TON-REPO --jq .size     # même chose en terminal
    Pour un dépôt privé, utilise gh api ou un token. Le chiffre peut avoir un peu de retard après un push. Si tu publies avec Actions, la taille de l’artefact github-pages dans le résumé du run donne une idée du site publié.

    Connaître la taille en local

    du -sh .                    # dossier complet
du -sh .git                 # historique seul
git count-objects -vH       # size-pack = taille compressée du dépôt
du -sh docs/                # le dossier publié (adapte le nom)

    Trouver les plus gros fichiers

    du -ah . --exclude=.git | sort -rh | head -10     # Linux
du -ah . | sort -rh | head -10                    # macOS

    Y compris ceux supprimés mais encore présents dans l’historique (taille en octets, puis chemin) :

    git rev-list --objects --all | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' | grep '^blob' | sort -k3 -rn | head -10
    Un gros fichier supprimé reste dans .git. Pour l’effacer vraiment de l’historique, utilise git filter-repo (voir la section Panique). Pour les gros fichiers à garder, préfère les releases ou Git LFS.
